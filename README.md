# 3D Maze — OpenGL 미로 게임 & 자체 회전체 모델러

2023년 중앙대학교 컴퓨터그래픽스 기말 프로젝트 (개인 작업)

C++ / OpenGL 고정 파이프라인으로 구현한 3D 미로 탐험 게임과, 게임에 사용할 3D 모델을
만들기 위해 직접 제작한 회전체(Surface of Revolution) 모델러입니다.
모델 데이터 생성부터 런타임 렌더링까지의 파이프라인을 전부 자체 구현했습니다.

```
SOR.exe (모델러)  ──►  *.dat (정점 + 면 인덱스)  ──►  Final.exe (런타임 로드)
```

## 실행

| 파일 | 설명 |
| --- | --- |
| `bin/Final.exe` | 미로 게임 본편 |
| `bin/SOR.exe` | 회전체 모델러 |

`freeglut.dll`이 함께 들어 있어 별도 설치 없이 실행됩니다. (Windows / x86)
콘솔 서브시스템 앱이라 실행 시 콘솔 창이 함께 뜹니다. SOR 모델러는 이 콘솔로 수치를 입력받습니다.

### 조작 — Final.exe

| 입력 | 동작 |
| --- | --- |
| `W` `A` `S` `D` | 전진 / 좌 / 후진 / 우 |
| 마우스 좌클릭 드래그 | 시점 회전 |
| `R` | 시작 지점으로 복귀 |
| `ESC` | 종료 |

> 개발 중에는 `Q` `E`로 카메라 높낮이를 조절하는 디버그 조작을 사용했고, 제출본에서는 비활성화했습니다.

### 목표

컨셉은 '우주 공간에 있는 정거장'입니다. 맵은 중앙 / 우측 / 좌측 / 후방 네 구역으로
나뉘며, 중앙 구역이 나머지 세 구역의 연결점 역할을 합니다.

좌·우·후방 구역에 배터리가 하나씩 숨겨져 있고, 3개를 모두 모으면 중앙 정면의 잠금
장치가 해제됩니다. 그 너머의 트로피에 도달하면 클리어입니다.

### 조작 — SOR.exe

회색 사분면 화면을 클릭해 정점을 찍고, 우클릭 메뉴로 기능을 실행합니다.

| 메뉴 | 동작 |
| --- | --- |
| `rotate` | 360의 약수를 입력받아 해당 각도씩 y축 회전, 회전체 정점군 생성 |
| `make face` | 정점 인덱스 3개 단위의 면(Face) 구조체 배열 생성 |
| `connect` | 생성된 면 순서대로 정점을 연결해 결과 폴리곤 미리보기 |
| `scale` | 정점 좌표 배율 조정 |
| `save` | 정점과 면을 `.dat`로 저장 |
| `clear` / `exit` | 초기화 / 종료 |

`rotate`는 입력값이 360의 약수가 아니면 다시 입력받습니다. 약수가 아닐 경우 한 바퀴가
정확히 닫히지 않아 회전체가 완성되지 않기 때문입니다.

## 구조

### 클래스 계층

오브젝트 종류마다 클래스를 늘리는 대신, 폴리곤 파일명(`string`)과 텍스처 ID(`int`)로
파라미터화해 아이템·장식·구조물을 같은 계층에서 처리하도록 설계했습니다.

```
MapObject                        기반 클래스
├─ position, direction, radius
├─ polygonName (string)          .dat 로드 키
├─ readModel()                   .dat 파서
├─ render()                      폴리곤 렌더링
└─ checkCollisionWithCamera()    거리 기반 획득 판정
     └ 사용처: 배터리 3, 트로피, 장식 행성 3, 행성 링 2

PlaneObject : MapObject          벽 / 바닥 / 천장
├─ direction_height, width, height
├─ texture (int)                 값에 따라 이미지와 반복 패턴 결정
├─ render()                      텍스처 매핑된 사각형
└─ collisionNavigation()         벽면 슬라이딩 충돌 처리
     └ 사용처: 133개 (Main 59 / Right 22 / Left 24 / Back 27 / Lock 1)
```

`PlaneObject`는 부모보다 벡터를 하나 더 받습니다. 위치 벡터 외에 사각형을 그릴 때 필요한
너비 방향과 높이 방향을 지정하기 위한 것으로, 두 벡터가 수직이 아니면 경고를 출력하고
외적으로 보정합니다.

구역별로 다른 텍스처 ID를 부여해 플레이어가 현재 어느 구역에 있는지 시각적으로 구분되게
했습니다. 같은 이미지라도 ID를 다르게 주면 렌더링 시 다른 반복 패턴이 적용됩니다.

### 벽 충돌 — 슬라이딩

단순 차단이 아니라 벽을 따라 미끄러지도록 처리했습니다.

1. 벽의 `direction`과 `direction_height`를 외적해 법선을 구함
2. 이동 예정 지점과 벽 평면의 거리, 그리고 벽의 너비·높이 범위 안에 드는지 검사
3. 충돌 시 이동 벡터를 벽의 `direction`에 투영 — 벽과 평행한 성분만 남김

충돌 판정을 벽 객체 / 카메라 / 외부 관리 코드 중 어디에 둘지가 이 프로젝트에서 가장
오래 고민한 부분입니다. 최종적으로 벽이 카메라의 위치·방향을 인자로 받는 구조로 정했고,
그 뒤로는 구현이 오히려 단순해졌습니다.

### 구역 스트리밍 (히스테리시스)

맵 전체(133개 벽)를 항상 유지하면 렌더링과 충돌 검사 비용이 커지므로,
카메라 좌표에 따라 구역 단위로 객체를 생성·해제합니다.

이때 경계에서 생성과 해제가 반복되는 스래싱을 막기 위해 **생성 임계값과 해제 임계값을
다르게** 두었습니다.

```cpp
if (cameraZ >  40.0f && !isRightGenerated) { generateWallsRight(); isRightGenerated = true;  }
if (cameraZ <  30.0f &&  isRightGenerated) { releaseWallsRight();  isRightGenerated = false; }
//         ^^ 10 단위의 히스테리시스 밴드
```

### `.dat` 포맷

텍스트 기반이며 `SOR.exe`가 출력하고 `MapObject::readModel()`이 파싱합니다.

```
VERTEX = <정점 수>
<x> <y> <z>          × 정점 수
FACE = <면 수>
<i0> <i1> <i2>       × 면 수
```

| 파일 | 정점 | 면 | 용도 |
| --- | ---: | ---: | --- |
| `trophy.dat` | 576 | 1152 | 트로피 (최종 목표) |
| `battery.dat` | 270 | 540 | 배터리 아이템 |
| `planet3.dat` | 192 | 384 | 장식 행성 |
| `polygon.dat` | 162 | 324 | 테스트 모델 |
| `planet1.dat` `planet2.dat` | 180 | 360 | 장식 행성 |
| `planet_ring.dat` `planet_ring2.dat` | 160 | 320 | 행성 고리 |

모든 모델이 `면 = 정점 × 2`입니다. 회전체의 사각형 세그먼트를 삼각형 2개로 분할하는
구조에서 나오는 결과입니다.

### 텍스처

`bin/Texture/`의 파일은 확장자가 모두 `.bmp`이지만, 실제로는 7개 중 6개가 JPEG입니다.

| 파일 | 실제 형식 | 해상도 |
| --- | --- | --- |
| `dia_panel` `metal_panel` `spacetile` | JPEG | 1000×1000 |
| `Gcircuit` | JPEG | 1000×700 |
| `Rcircuit` | JPEG | 1000×634 |
| `steel` | JPEG | 500×500 |
| `check` | BMP | 256×256 |

당시 SOIL의 `SOIL_LOAD_AUTO`가 확장자가 아니라 파일 내용으로 형식을 판별했기 때문에
문제없이 동작했습니다. 교체한 stb_image도 동일하게 내용 기반으로 판별합니다.

## 빌드

### 요구 사항

| 항목 | 값 |
| --- | --- |
| IDE | Visual Studio 2022 (C++를 사용한 데스크톱 개발) |
| 툴셋 | MSVC v143 (원본 빌드는 v14.37) |
| **플랫폼** | **x86 (Win32)** — 동봉된 `freeglut.dll`이 32비트입니다 |
| 확인 환경 | Visual Studio 2022 (v145 툴셋), vcpkg, x86 Debug/Release 빌드 및 실행 확인 |
| 서브시스템 | 콘솔 |

### 의존 라이브러리 (모두 32비트)

| 라이브러리 | 용도 | 조달 |
| --- | --- | --- |
| FreeGLUT | 윈도우·입력·메인 루프 | vcpkg (`freeglut:x86-windows`) |
| GLM | 벡터/행렬 연산 (헤더 전용) | vcpkg (`glm:x86-windows`) |
| stb_image | 텍스처 디코딩 | **저장소에 포함** (`src/stb_image.h`) |

원본은 텍스처 로딩에 SOIL을 사용했으나, 2008년 이후 개발이 중단되어 최신 MSVC에서
빌드가 어렵습니다. SOIL이 내부적으로 사용하던 **stb_image를 직접 링크하는 방식으로
교체**했습니다. 디코더가 동일하므로 로딩 동작에는 차이가 없고, 단일 헤더라 별도 빌드가
필요 없습니다.

### 빌드 절차

솔루션과 프로젝트 파일이 저장소에 포함되어 있어 별도 설정이 필요 없습니다.

1. [vcpkg](https://github.com/microsoft/vcpkg)를 설치하고 32비트 의존성을 받습니다.

   ```
   vcpkg install freeglut:x86-windows glm:x86-windows
   vcpkg integrate install
   ```

2. `3DMaze/3DMaze.slnx`를 Visual Studio 2022로 엽니다.
3. 플랫폼이 **x86**인지 확인하고 빌드합니다. (Ctrl+Shift+B)
4. Ctrl+F5로 실행합니다.

`vcpkg integrate install`이 포함/라이브러리 경로 설정과 `freeglut.dll` 복사를 자동으로
처리합니다. Debug 구성은 `freeglutd.dll`, Release 구성은 `freeglut.dll`이 복사됩니다.

프로젝트 파일에 미리 적용해 둔 설정입니다.

| 항목 | 값 | 이유 |
| --- | --- | --- |
| SDL 검사 | 해제(`/sdl-`) | `/sdl`은 `_CRT_SECURE_NO_WARNINGS`를 무시하고 `fopen`/`fscanf` 경고를 에러로 승격시킵니다 |
| 디버거 작업 디렉터리 | `$(ProjectDir)` | 아래 실행 경로 참조 |
| 하위 시스템 | 콘솔 | 모델 로드 실패 등의 메시지를 콘솔로 출력합니다 |

### ⚠️ 실행 경로

`MapObject::readModel()`이 `_chdir("../bin/")`으로 작업 디렉터리를 옮기고, 텍스처 경로도
`"../bin/Texture/..."`로 잡혀 있습니다. 따라서 **작업 디렉터리는 `bin/`을 포함한 폴더의
직속 하위여야** 합니다.

프로젝트가 `3D_Maze/3DMaze/`에 있으므로 `$(ProjectDir)`가 이 조건을 만족합니다.

```
$(ProjectDir) = 3D_Maze/3DMaze/
    → _chdir("../bin/")  →  3D_Maze/bin/     ✓
```

프로젝트 폴더를 다른 깊이로 옮기면 이 경로가 깨집니다. 콘솔에 `No file`이 반복되면
작업 디렉터리를 먼저 확인하세요.

### 배포

`_chdir("../bin/")`는 `bin/` 안에서 실행할 때도 성립합니다 (`bin/../bin/` = `bin/`).
따라서 배포는 실행 파일과 DLL을 리소스와 함께 `bin/`에 넣는 단일 폴더 구성이 가장
간단하며, 2023년 제출본이 이 구조입니다.

```
배포 폴더/
└── bin/
    ├── Final.exe
    ├── freeglut.dll
    ├── *.dat        (모델 8종)
    └── Texture/     (텍스처 7종)
```

## 이후 리팩터링

당시 개발 중 "벽면 텍스처가 무작위로 다른 이미지로 바뀌는" 현상이 있었고, 그때는
원인을 특정하지 못한 채 거리 컬링으로 증상만 완화했습니다. 이후 코드를 다시 분석해
근본 원인을 규명하고 정리한 내역입니다.

| 커밋 | 내용 |
| --- | --- |
| `fix` | `PlaneObject::textureID` 미초기화 수정 — 생성자에서 초기화되지 않은 값을 `glDeleteTextures`에 넘겨 **다른 객체의 텍스처를 삭제**하고 있었음. 텍스처 오염의 근본 원인 |
| `perf` | 텍스처 캐싱 도입 — 벽마다 새 ID를 발급하던 것을 경로 기준으로 공유. 텍스처 생성 **133개 → 7개** |
| `perf` | 면 단위 `glBegin`/`glEnd`/`glPolygonMode` 호출을 루프 밖으로. `trophy.dat` 기준 프레임당 **1152쌍 → 1쌍** |
| `fix` | 모델 로드 실패 시 미초기화 `pnum`/`fnum`으로 순회하던 문제, `delete[]` 후 댕글링 포인터 방지 |
| `fix` | 잠금 해제 후 `lockExists` 플래그를 내리지 않아 매 입력마다 해제 함수가 반복 호출되던 문제 |
| `refactor` | `glm::radians(glm::degrees(x))` 무의미한 단위 왕복 제거 |
| `chore` | SOIL → stb_image 교체. 외부 라이브러리 빌드 없이 재현 가능하도록 단일 헤더를 저장소에 포함 |

`bin/` 안의 실행 파일은 **2023년 제출 당시 빌드본**이며 위 수정은 반영되어 있지 않습니다.

### 아직 남겨둔 것

- `_chdir("../bin/")`이 생성자에서 프로세스 작업 디렉터리를 바꾸는 부작용. 현재 호출
  순서에서 우연히 멱등하게 동작하고 있어, 리소스 경로 처리를 함께 정리할 때 손볼 예정
- `MapObject` 생성자에서 가상 함수 `readModel()`을 호출하는 구조. 파생 클래스의 오버라이드가
  호출되지 않으나, 기본 인자 `""`로 조기 반환되어 결과적으로는 동작
- 렌더링 컬링 범위와 충돌 검사 컬링 범위가 서로 다름. 현재 맵 배치에서는 증상이 없음

## 회고

프로젝트가 커질수록 단순 논리 구조뿐 아니라 종속성, 파일 경로, 라이브러리 연결, 상속
계층과 상·하위 객체 분류까지 신경 쓸 것이 많다는 걸 배웠습니다. 시작할 때 무작정 헤더
파일을 많이 만들었다가 코드가 꼬였던 경험이 특히 그렇습니다.

기능 구현을 우선한 대가는 후반의 최적화 비용으로 돌아왔고, 당시에는 원인을 특정하지 못한
채 증상만 덮었습니다. 시간이 지나 코드를 다시 읽고서야 근본 원인을 찾았는데, **증상 완화와
원인 제거는 다르다**는 것이 이 프로젝트에서 가장 오래 남은 교훈입니다.
